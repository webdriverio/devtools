- **Network has three sources, and the page's Resource Timing is the floor.** BiDi (all four adapters) and Nightwatch's Chrome performance log are driver-side and carry headers and status. The page collector carries two: its patched `fetch`/`XMLHttpRequest` (the only source with bodies) and the document's Resource Timing buffer (`script/src/collectors/resourceTiming.ts`): every load with timing phases and size, a status on Chromium only, never headers. Resource Timing is the only network source a browser without BiDi has, which is Safari and every Appium session (Appium's BiDi reference lists `session.*` alone). The collector reads the buffer at construction, which is what covers loads made before a `<script>`-injected collector existed, then observes; a second evaluation of the bundle in the same document keeps the first collector (next entry), so the buffer is read once per document. Its two page sources are deduplicated inside the collector: the patch *claims* each call (absolute URL without fragment, which is the form the buffer names, plus start time), a `fetch`/`xmlhttprequest` entry within 1 s of a claim is taken so the row with headers and body is the one kept, and because the entry can arrive before the call has answered, a taken entry is *held* until the patch records the call (the entry is then its second listing and dropped) or drops it (no content-type, a rejected fetch, an XHR `error`/`abort`/`timeout`: the held entry becomes the request's only record). Recording a failed call as a failed row instead was tried and reverted: the service and Nightwatch keep the page's patched rows beside BiDi's, so on Chrome every blocked beacon was listed twice (Nightwatch example 35 → 67 failure rows); without BiDi a failed call therefore reads as unknown rather than failed, which is the entry's own account of it. Against a driver-side source the gate is `processTracePayload`'s `skipResourceTimingRequests`, which drops only the Resource Timing rows and leaves the patched rows their bodies, and **the gate is evidence, not a subscription**: measured on Appium 3.7's XCUITest driver, selenium-webdriver's BiDi inspectors attach cleanly and then deliver nothing, so gating on `bidiActive` (or on `browser.isBidi`) withheld the page's rows and the trace had zero network rows. Each adapter therefore latches on the first BiDi network event it receives (service `#bidiNetworkObserved`, set in `handleNetworkRequestStarted`; Selenium and Nightwatch `bidiNetworkObserved`, set in their `buildBidiSinks`; Python `stats["observed"]`, read by `bidi.network_serving`) and gates on that. Nightwatch's performance log is deliberately **not** a gate either: a capability can name a log the driver never serves (XCUITest), and the log is read after the drain in any case, so `perfLogs.ts` `upgradeResourceTimingRows` pairs each log entry with the page's row for the same load (URL, nearest `timestamp`, the log's being dated from CDP's `wallTime` because the monotonic clock only diffs within a session) and lays the log's method, headers, status and size over that row, keeping the row's id, clock and measured phases, and re-sends it under the id, which the dashboard replaces in place. The reverse order is covered too: a load that completes between the drain and the log read reaches the session as the log's row first, so the session keeps it in `loadsListedByLog` until the next drain, where `withoutLoadsTheLogListed` spends it on the page's one row for it (same URL, nearest `timestamp` within 2 s). A ledger spent per load, not a scan of the rows the session holds: the scan read the collector's own patched fetch row, or a row the log had already upgraded, as the listing of a *second* request to that URL inside the window and dropped that request outright (a fetch answered with a content-type-less 204 after one answered with JSON lost its only row). Spent at the next drain that reaches the driver, a collector-less document included, and forgotten at a session replacement (`armReplacedSession`), because the page observed the load before the log could list it: a row absent from that drain is never coming, and a load kept longer would take the row of the next request to the same URL. Residual, Chrome only (Safari and Appium serve no log, so the ledger stays empty there): the log also lists the collector's own patched fetch/XHR calls, whose row is not a Resource Timing row, so `upgradeResourceTimingRows` appends the log's row beside the patched one (main ingested both too) and the ledger can spend it on the row of a different request to that URL inside the window, as it can on the next document's load of a shared asset; the request then survives as its own log row, without the page's phases, so the cost is a row's shape rather than a request. Python withholds the whole page batch once BiDi is serving, as selenium-devtools does (whose console gate, `bidiConsoleObserved`, is evidence-based for the same reason); both lose the patched rows' bodies there rather than list each fetch twice beside its BiDi row, which is what the service's keep does. Residuals: a drain that lands before the first BiDi event of a page is delivered can pass that page's rows once, and Nightwatch clears both flags at a session rotation, so loads in the window before BiDi re-attaches can be listed by both.
  - **A second evaluation of the collector bundle in one document keeps the first collector.** Every adapter probes for the collector before injecting, but two callers can pass the probe before either injection has run (Nightwatch's navigation proxy and its drain's recovery, Selenium's navigation hook and its recovery), and a second evaluation that replaced `window.wdioTraceCollector` would drop everything the first had buffered. Measured on Android Chrome through Appium, where there is no BiDi and the `<script>` path is the only one: Nightwatch injected twice 11 ms apart and the trace had **0 network rows** for a run that loaded two pages, because the replacement also could not re-read the Resource Timing buffer without listing the first collector's loads again. `collector.ts` exports `alreadyInstalled` and keeps the instance it finds, and `index.ts` skips its bootstrap on that flag, so the second script is a no-op rather than a second observer feeding the same collector; the adapters' probes only save the round trips. The `chrome-native:` new-tab document a mobile Chrome session opens on is ignored with the rest of the browser's own schemes, since a session starts there before its first navigation; that list is `shared/browser-schemes.ts`, read by core's injection gate and the collector's request filter alike, so the two cannot drift again.
  - **selenium-webdriver's `NetworkInspector` hands every network event to every subscriber's callback** (`_on` adds one unfiltered socket listener per subscription), so `core/bidi.ts` `handleBidiRequestSent` also receives response events and `handleBidiResponseCompleted` request events. Unguarded, the request handler pushed a second, never-completed row per request and the response handler finalized rows on request events: measured, every request in a Selenium Chrome trace listed twice (a status-0 row beside the completed one) and 57 of 135 rows in a Nightwatch one. Each handler now ignores the other's event by shape (`response` present or absent). Two more shapes the inspector does not model: a redirect hop re-sends the request under the same id, so rows are kept by id for the session (bounded at 5000, oldest out) and a request for a known id reopens its row under the first hop's clock rather than pushing one; and a failed fetch, which core closes as a failure (status 0, the browser's `errorText`, as the WDIO service's `handleNetworkFetchError` already did) through the inspector's `fetchError` hook, reading `network.fetchError` off the inspector's own connection only for an inspector without one; that handler ignores the request and response events the same dispatch hands it, by `errorText`. Without that, every blocked analytics beacon sat in the Network tab as pending for the life of the session; a browser that refuses the subscription keeps the inspector and only that gap.
  - A Resource Timing row states `source: 'resource-timing'`, the list colours it `unknown` rather than `pending` when it has no status, the detail card names what it could not see, and the HAR writer adds `_source` and `_resourceType`: HAR's required `status` is written as 0 for it, which read back as-is is a transport failure, and an empty `content.mimeType` cannot restore the type. The method is `''` for a navigation, fetch or beacon (Resource Timing names none) and `GET` only for a parser-initiated load. A native app session has no document and therefore no page-side network capture. All four adapters read its traffic from the appium-interceptor plugin's proxy when the session sets `appium:intercept: true`: `core/appium-interceptor.ts` `NativeNetworkCapture` owns the per-session listener and its drains, and each JS adapter supplies only an execute path that renders no rows (the service and Nightwatch raw WebDriver HTTP bound to the session, Selenium the unpatched `executeScript`) plus its drain points (after each command, before a per-test slice is written, at session end). Every read returns the listener's whole history, bodies included, so the per-command drains are throttled to `NATIVE_NETWORK_DRAIN_INTERVAL_MS` while the test-end and session-end drains never are. Python mirrors it in `selenium_devtools/interceptor_network.py`, since it ships no Node, and drains when each test reports its outcome. `appium:intercept` is honoured flat or grouped under `appium:options`. The plugin records no timing, so each row is stamped when first read, and requests made before the listener starts (an app's launch traffic) are not listed.
