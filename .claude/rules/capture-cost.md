### What a per-action trace capture costs

- **Measure before proposing a change: `DEVTOOLS_CAPTURE_TIMING=1`.** Every adapter then times each probe of each capture (issue and settle, so a probe's own service time is separable from its wait behind the probes the driver served first) and, when the trace is written, prints a per-probe table and appends the raw records to `capture-timing-<pid>.ndjson` beside the trace. The JS recording is `core/capture-timing.ts`, wired once in `captureActionSnapshot` and reported from `finalizeTraceExport`, so no adapter carries more than the capture's trigger (action, wait poll, matcher poll, final); Python mirrors it in `capture_timing.py`, held to the same summary by `mirror-vectors.json`. Off, it costs a flag read per capture. The per-platform commands are in the README's "Measuring capture cost". The polling filmstrip recorder's own screenshots are counted beside it (`recordRecorderShot`/`recordRecorderSkip`/`recordRecorderReuse`, one `filmstrip recorder:` line, not written to the NDJSON); Python has no polling recorder and prints none, so the mirrored summary is unchanged. The shot durations are a ring of the newest 2000 (`RECORDER_SHOT_SAMPLE_MAX`), since a live run never reports and never drains them.
- **One capture per action means two driver round trips per action, and the platform decides which half is expensive.** Measured on Appium 3.7.0 / UiAutomator2 (emulator-5554, Android API 37, 1080×2424): `GET /screenshot` 1.18–2.22 s (steady ~1.20 s) at 1.86 MB, `GET /source` (page-source XML) 0.09–0.53 s at 40 KB, `window/rect` 0.015 s; the screenshot dominates by ~10× on Android. A later timing run (v11.2.0, `DEVTOOLS_CAPTURE_TIMING=1`, a loaded machine, so rough) split an Android WebdriverIO capture about evenly between the two (384-471 ms per capture) and put the page source at **817 ms of a 938 ms iOS capture (87%)**: the split inverts on iOS. Measured per action: two captures 2.41 s against one capture 1.19 s; end-to-end on the native example 19.1 s against 12.4 s, with live mode (no per-action capture) at 5.9 s. That is the case for the `beforeCommand` capture, and the reason an eager post-action capture is not worth re-adding: it cost a second capture per action and existed only to be patched by a `readyState` poll that could not tell a document that had not navigated yet from one that was loading.
- **A native capture is the screenshot plus the page source, in every JS adapter.** A native app serves no page script, url or title, so core's `captureActionSnapshot` builds the element list, the accessibility tree and the locators from the page-source XML instead (`fromPageSource`), and an adapter only supplies the reader: the service `getPageSource` (or its direct probe), Selenium the unpatched original (`getDriverOriginals().getPageSource`, so the read is never a row of the user's), Nightwatch `GET /source` over the raw WebDriver transport. The Selenium and Nightwatch adapters ask core's `SessionCapturer.nativeApp` (`nativeAppOf`), which carries the platform the XML is read by (none for a Mac2 or tvOS app, read as Android). A reader passed is also what marks the capture `native` in the timing report and times its `pageSource` probe. The read is the costly half of a native capture (above), so trace mode on iOS pays for it on every action. Python takes the screenshot alone on a native app (`_page_trees_enabled`, `instrumentation.py`, is false on a native app, so the page reads are skipped and no source is read), so its native traces carry no element list or accessibility tree.
- **Locator generation from a native page source must stay linear, and iOS is where it did not.** Every native action snapshot builds element locators from the page-source XML (`core/locators`), and each uniqueness check was a `//*[@name="…"]` XPath run by the `xpath` library over the whole document, several per element. Measured on the iOS Settings page source tiled up: 38 KB 82 ms, 188 KB 1.4 s, 752 KB 23.5 s, which is what a reporter saw as trace mode adding 1.5 min to a 2 min 20 s iOS test while Android, with smaller flatter trees, added 10 s. `locators/xpath-index.ts` indexes the document once per `generateAllElementLocators` walk (`withXPathIndex`) and answers `//*`, `//Tag` and `//Tag[@a="x" and …]` from it: 15 ms, 49 ms, 268 ms for the same three, identical elements. It is scoped to the walk so a caller of the exported `evaluateXPath` that edits its document is never answered stale, and it declines a namespaced document, where XPath name tests resolve namespaces and the index does not. The page-source request itself remains: 0.75-1.2 s per action on XCUITest even for Settings, against 0.09-0.5 s on UiAutomator2.
- A filmstrip poll against a native session stacks requests: `setInterval` never waits for its async handler, a native screenshot takes ~1.2 s against the 200 ms default, and a serialised driver serves that queue ahead of the test's own commands; measured, a **15 ms command took 4.5–7.8 s**. `ScreencastRecorderBase`'s `#pollInFlight` latch bounds it to one outstanding shot, and `#pollGeneration` stops a shot orphaned by `stop()` from appending after the stop or clearing its successor's latch. One outstanding shot still queues in front of everything after it (measured: a per-action screenshot 600-665 ms on the Android emulator with the poller running, 229 ms without), so a tick is also skipped while the driver is held: `core/driver-activity.ts` keeps one bounded in-flight gate per adapter bundle, opened by each adapter's command hook (`beginDriverCommand`, the service's `beforeCommand`, Selenium's patched methods, Nightwatch's proxy at enqueue) and by `captureActionSnapshot` around its probes (`beginDriverCapture`). A wait and a host-side command (`pause`, `perform`, ...) open none (shared `occupiesDriver`): the driver is idle between a wait's polls, and a pause holding the gate would blank the filmstrip for nothing. A skipped tick is dropped rather than deferred, so a run of commands that take no capture (reads, lookups, wait polls, every command of a live run) would starve the filmstrip: once the newest frame is `MAX_FILMSTRIP_GAP_INTERVALS` (3) intervals old the recorder polls through a busy driver anyway, one shot at a time; that poll still waits behind the command and takes its own screenshot time, so the longest gap is about three intervals plus one screenshot. The gate tags each window (`DriverWindowKind`) and two kinds are never overridden: input (`isInputDispatchInFlight`, shared `isInputDispatchingCommand`, which names the WebDriver protocol commands WDIO re-runs its hooks for inside `click`/`setValue`, since the service keeps one window and the nested one replaces it), because a screenshot between chromedriver's coordinate read and its dispatch makes the click report success and activate nothing; and a capture (`isCaptureInFlight`), whose own screenshot is the frame, where a capped poll would only queue behind it on a 1.4 to 2.4 s native capture and hold the driver in front of the next command. Selenium's `actions().perform()` reaches the driver through `execute()`, so `actions-patcher.ts` opens its input window itself. The service opens no window for its own injection calls (`#afterCommand` returns before closing one while `#injecting`), and Nightwatch opens one only for a command known to call back from the driver (`helpers/commandWindow.ts`), since its window closes from the appended callback and a builder API (`actions()`, v3's scoped `browser.element()`) or a custom command that never calls back would hold the gate to its bound. Each per-action capture's screenshot is offered to the recorder as a frame stamped when it settled (`ScreencastRecorderBase.offerCapturedFrame`), and the next tick within one interval is skipped as redundant. The offer is taken only when exactly one recorder is recording in the process and it polls, since the capture names no session; a shot no newer than the newest frame is dropped rather than reordered. Residuals: the gate is process-wide, so in a multi-session process one session's commands also hold the other's poller off; a recorder never stopped stays in the registry and disables reuse for the process; a reused frame still passes through `maxBufferFrames` decimation and export thinning like a polled one; after a failed assert, Nightwatch's aborted queue strands the input windows of commands enqueued after it, so for up to 3 s the recorder takes no polled frame (trace mode still gets reused capture frames).
- **`start()` and `stop()` are serialised against each other, because unserialised neither owns what it arms.** A `stop()` landing mid-handshake returned at its `#isRecording` guard — still false, the handshake not having finished — so it never reached its own CDP teardown, and the `start()` it interrupted then returned on the generation mismatch without stopping what it had armed: the session and its frame listener stayed live after teardown. The frames themselves were moot — every adapter builds a fresh recorder per session (the service's `packages/service/src/screencast-lifecycle.ts` does so even across `reloadSession`), so the leaked session and its browser-side stream were the damage, not buffer pollution. The obvious repair — stopping the session on that mismatch path — is wrong, and it is the shape to keep out: it guards a field both CDP overrides write at handshake **start** (the service's `#cdpSession` in `packages/service/src/screencast.ts`, Selenium's `#cdp` in `packages/selenium-devtools/src/screencast.ts`) with a flag core sets only at handshake **end** (`#cdpActive` in `packages/core/src/screencast.ts`), so a start arriving in that window is indistinguishable from no start at all and the stale path tears down the *newer* recording's session instead. Overlapping starts are the adapters' normal mode rather than a corner: Selenium's `driverPatcher` documents the second test's body racing an in-flight `screencast.start()`, and Nightwatch's session rotation is fire-and-forget from a command hook. Queued, a stop always runs against a start that has finished arming and owns what it armed, which makes the mismatch branch unreachable and deleted — the tick-phase generation checks in `#startPolling` are **not**, since a shot orphaned by a stop still lands afterwards. Two consequences: `stop()` waits on an in-flight handshake, and every awaited driver primitive in that handshake is ceilinged at `SCREENCAST_HANDSHAKE_TIMEOUT_MS` (the service's `getPuppeteer()`/`pages()`/`createCDPSession()`/`Page.startScreencast` and the stop-side `Page.stopScreencast`, Selenium's `createCDPConnection` and the capabilities read that decides whether to call it, the polling path's first screenshot) — a driver that wedges gives up after the ceiling, falls back to polling, or reports the screencast unavailable when polling was what wedged. Nothing is claimed until the handshake has answered, so a timed-out start leaves nothing armed — and a session or connection that completes after the ceiling is detached (or its socket closed) when it lands, so no orphan outlives the recording. And a stop landing during a polling session's first screenshot records that shot before tearing the loop down; the interval is still never left armed underneath the stop.
- A pre-capture stamps `Date.now()` when the timestamp it scans predates `#currentTestStartWallTime`, because the log it scans is run-long and a test boundary is invisible to it: the scanned timestamp would be the previous test's last action, whose slot already holds that test's finalize capture, and the richer-screenshot merge could replace it (with a `reloadSession` between the tests the row replayed the post-reload page). In the service and Nightwatch, `#currentTestStartWallTime` is 0 without per-test hooks, so a standalone run is unaffected (Selenium initialises it to `Date.now()`); this is the same rule that makes a session's first capture its initial frame. Per-test slices are unaffected: `flushTest` runs inside `afterTest`, before the next test's commands.
