# core — design notes and known debt

Owns the framework-agnostic capture, reporting and transport logic that the three JS adapters share (`packages/core/src`).

## Design notes

Selenium, Nightwatch and Python skip a capture only for a command `skipsCapture` (`shared/trace-actions.ts`) knows is a read, wait or lookup, and capture after every other command, including unmapped ones that can navigate (`executeScript`, `actions`, Nightwatch `submitForm`). A test's first mapped command always takes one. Selenium and Nightwatch (selenium `commandPostActions.ts` `queueActionSnapshot`, nightwatch `SessionCapturer#queueActionSnapshot`) capture right after the command itself. Rows after a test's last capture mean that capture saw a state the test later left, so the test takes one more capture at its end, stamped at that last capture (`core/final-frame.ts` `finalFrameStamp`) and superseding that record field by field, only when it has a screenshot; this covers a click that returns before its navigation commits. A test ending on a capturing command pays nothing. WDIO applies the same gate, but only to commands it renders as action rows, and captures before the next command rather than after its own, so it takes no end-of-test frame. In the JS adapters and Python a read, wait or lookup takes no capture, and inherits the latest earlier one through `claimAfter`. In Python the capture includes the command's screenshot, so trace mode takes no screenshot for a read at all (`instrumentation.py` `_takes_capture`, held to core's gate by the `captureGate` mirror-vectors section); on a native app the capture is that screenshot alone, recorded as an action snapshot so the end-of-test capture can supersede it. Live mode still screenshots every command row, which is the dashboard's only picture of a native app. Without a pushed CDP stream those screenshots are also Python's filmstrip (there is no poller), so a command that takes no capture still takes a filmstrip-only frame (`_filmstrip_frame_due`): every command a `WebDriverWait` issues that returns (a poll that raises takes none), and any other read once shared's `SCREENCAST_DEFAULTS.pollIntervalMs` (generated as `SCREENCAST_POLL_INTERVAL_MS`) has passed since the last frame; the end-of-test capture is a frame too.

## Known debt

- `replaceCommand` has two semantics — Selenium mutates in place (`selenium-devtools/src/session.ts`, preserves `_id`/`id` for chained calls); Nightwatch splices and reissues (`nightwatch-devtools/src/session.ts`); the storage strategy stays adapter-specific because runner integrations differ. Could be unified by parameterizing the policy if the divergence ever causes a real problem.

- BiDi is auto-attached in Service and Selenium; Nightwatch is opt-in via `bidi: true` and requires `webSocketUrl: true` in capabilities.

- Retry-aware trace policies share one mechanism: adapters feed a per-attempt **outcome ledger** (`core/attempt-tracker.ts` `TestAttemptTracker.recordStart(uid, specFile)` + `recordOutcome(uid, state, attempt)`) keyed by the **retry-stable** uid, and the finalizer reads the scoped views (`all`/`forSpec`/`forTest`) so `packages/trace/src/trace-retention.ts` evaluates **group-by-test** — `retain-on-failure` keys on each test's *final* attempt (no over-retaining a fail-then-pass), `retain-on-first-failure` on *attempt 0*. `recordStart` on a second attempt stamps the prior attempt `failed` (a retry only follows a failure), which corrects runners that swallow the intermediate failure — e.g. Mocha via a `--require` plugin never surfaces the retried attempt's failure, so the ledger would otherwise see `[passed, passed]`. An empty scoped view falls back to `testMetadata` (never fail-open-retains).
  - **WDIO + Selenium: verified end-to-end** (manual fail-then-pass runs: retained under `retain-on-first-failure`, dropped under `retain-on-failure`).
  - **Nightwatch: `retain-on-failure` works; the other retry-aware policies degrade.** Its `--retries` re-runs the testcase *internally* without re-firing the plugin's per-test hooks, and the per-testcase results carry no attempt/retry field (retries live only in undocumented, version-varying Nightwatch internals — `suiteRetries.testRetriesCount` / `reporter.testResults.retryTest`), so the ledger sees only the final attempt for the `describe/it` and exports-object interfaces. Cucumber scenarios expose per-scenario hooks, so the feed captures their attempts. Not cleanly fixable without depending on those internals.
  - WDIO `specFileRetries` spawns a fresh worker per retry, so cross-process attempts aren't in the (process-scoped) ledger.

- Run identity across worker sockets is env-propagated. `core/run-id.ts` `resolveRunId()` publishes `DEVTOOLS_RUN_ID` (`RUNNER_ENV.RUN_ID`) and every worker socket carries it as `?runId=` (`WORKER_WS_QUERY`), so the backend keeps accumulated run state when the *next spec's* worker connects and wipes it only for a genuinely new run. Without it every connect reads as a new run: Preserve & Rerun 409s for every spec except the last one that ran, and a dashboard opened mid-run replays only the current spec. The WDIO service stamps it in the launcher's `onPrepare`, before workers fork, so all workers of one run agree; single-process adapters self-stamp on first use. **Gap: multi-process parallel runs in Selenium/Nightwatch** (jest/vitest workers, nightwatch `test_workers`) load the plugin per worker with no launcher-side hook to stamp first, so each worker generates its own id and still reads as a new run — a known gap, not a regression. Deriving the fallback from `process.ppid` would group those siblings, but would also make two sequential single-process runs share an id and inherit each other's state against a standalone dashboard, so the per-process fallback stands.

- **A trace archive is a full recording of the page, and there is no redaction policy anywhere in capture.** Whatever the run put on screen or typed is in the zip, usually several times over: measured on the Python login example, its demo credential appears ~103 times across six places — the page's own displayed text (90x, the-internet prints it), the DOM mutation stream, the `Element.fill` command args, the transcript, the captured test source, and `*-elements.json`. `shared/element-scripts.ts` blanks an `<input type="password">` value, which is worth having because nothing downstream reads that field, but it removes **2 of those ~103** and closes nothing on its own. `buildElementScripts` projects a captured record down to `CAPTURED_ELEMENT_FIELDS` (`packages/shared/src/element-scripts.ts`; `selector` and `boundingBox` are what the trace reads, the rest is context for a reader), so `value` and `href` leave the archive entirely — justified as dead data, **not** as a redaction: the same archive still carries 15 hrefs in `trace.mutations` independent of `elements.json`, and 29 `value` attribute mutations recording a typed string keystroke by keystroke (`t`, `to`, `tom`, ...). `@wdio/elements` keeps returning the full `BrowserElementInfo` from its own live call, which is its documented API. A real policy has to act at the collector and the command-arg serializer — a masking-selector or `maskInputs` option — not at one resource. Until then, treat a trace zip as sensitive as the run that produced it.

- **An `ActionSnapshot` carries no session identity, in any adapter.** `shared`'s type has never had one and `core/action-snapshot.ts` records none, so per-action captures from two concurrently-driven sessions land in one list and are resolved purely by the command's completion timestamp. `claimAfter` is an exact keyed lookup, so the window is narrow — two commands completing in the **same millisecond**, where `trace-frame-snapshots.ts` breaks the tie by "keep the richest capture" (largest screenshot), which is session-blind — plus the documented `latestAtOrBefore` fallback for a command that took no capture of its own. Python is not worse than the JS adapters here and leans on that fallback less, since it stamps each snapshot with its own command's `row["timestamp"]`; reaching the failure at all needs threaded drivers in one process (pytest's function-scoped fixtures are sequential, and `-n` is multi-process). Fixing it is a shared-contract change: `sessionId` on the snapshot, and an index keyed by the pair.

- **Live mode has no per-action DOM snapshot, so its replay is only as fresh as the last drain.** Per-action snapshots cost two injected scripts plus a screenshot and stay trace-only; all three adapters instead drain the collector after a command that could have moved the page. Service: `#drainAfterLiveCommand`. Selenium: `commandPostActions.ts` `warrantsLiveDrain` + `SessionCapturer.drainAfterLiveCommand`, the same deny-list shape over its own command vocabulary plus `mapAssertCommand` (a node:assert row never reaches the browser) — the predicate is *not* in core because the vocabularies are per-framework and only two `includes` calls would be shared. Draining only at navigation is not enough, because that hook is deferred behind an injection and a 500 ms settle: on the login example it leaves 2 mutation entries and 2 anchors for a 16-row run, so the page test 1 spends most of its life on is never anchored and all 11 of its rows replay the page the test *ended* on. Selenium's drain is serialized on a tail because the driver patcher does not await `onCommand`, and the app scans the mutation stream in order and stops at the first entry past a row's window — an overtaken batch strands every row after it.

- **A command row is stamped at COMPLETION, and the DOM anchor carries the document's own birth time.** These two together are what make the replay line up. (a) `selenium-devtools/src/driverPatcher.ts` and `nightwatch-devtools/src/helpers/browserProxy.ts` run their capture at completion, stamp `timestamp` with the completion clock and keep the invocation time as `startTime`. The page-side mutation stream is on real time, so an invocation-stamped row ends before its own effect lands and replays the page from before it — the `#username` fill rendered an empty field, the `#password` fill rendered only the username, and a navigation row rendered the page it had just left. Rows span their real duration, not a synthetic 1 ms. (b) `collector.captureCurrentDom` (the only producer of a mutation with a `url`) stamps `performance.timeOrigin`, not the drain clock. A drain is forced from Node whenever a collector might be fresh, which is always after the navigation — a round trip at best, a whole page load at worst — so drain-stamping put the anchor after several later actions (measured: 9/15 Selenium and 8/15 Nightwatch rows on the wrong DOM). With both in place a navigation row ends after its destination document was born, so the anchor needs no repositioning at all.
  - `packages/trace/src/trace-mutations.ts` `reattributeDomAnchors` remains as a narrow backstop for the one case the stamps can't cover: an anchor born *after* the last logged command, i.e. a click whose navigation commits once the click has already returned. It snaps such an anchor to the newest logged command, but **only when no logged command completed after it** — if one did, that command's row already resolves the anchor and pulling it earlier mis-credits it to a preceding action and steals the new page's DOM from rows still on the old one (measured: a 206 ms pull moved `/login` onto two rows that were on `/add_remove_elements`). Anchors are only pulled earlier, never past the newest timestamp already in the stream, or replay would apply the outgoing document's refs to the incoming tree.
  - Residual, accepted: Nightwatch's `click` resolves *before* its navigation commits (measured 5 ms), so a submit-click row can still show its pre-navigation page. Selenium is immune — its click waits for page load. Not worth another heuristic; every heuristic tried here regressed a different row.

- **Every per-action snapshot probe is timeout-guarded** (`core/action-snapshot.ts` `probe`, `SNAPSHOT_DRIVER_PROBE_TIMEOUT_MS`), not just the in-page scripts. Nightwatch's `browser.getCurrentUrl()`/`getTitle()` are QUEUED commands: called from inside the plugin's own command hook they enqueue behind the command still running and never resolve, and one unguarded probe in the capture's `Promise.all` stranded the whole snapshot — 10 of 14 captures never settled, so those actions reached the trace with no DOM, no a11y tree and no element rects. Nightwatch runs all four probes (url/title/screenshot/script) over the raw WebDriver HTTP transport in `nightwatch-devtools/src/helpers/webdriverHttp.ts`, bypassing the queue entirely — the pattern `takeScreenshotViaHttp` already used. Relatedly, `runWith` treats a `null` script result as its fallback: a driver that answers `null` instead of rejecting (no-such-session, transport-swallowed script error) otherwise handed the serializers a non-array and lost the entire snapshot, screenshot and all.

- The `filmstrip` option (dense screencast into the trace) is on **`BaseDevToolsOptions`** — the counterexample to the screenshot/video entry in `packages/service/CLAUDE.md` — because all three adapters implement it (the "second consumer → base" rule realized). Core owns the work (`packages/trace/src/screencast-trace.ts` `thinScreencastFrames`/`buildDenseScreencast`; slice windowing in `spec-trace-helpers.ts`); adapters only default the option, un-gate the recorder in trace mode when it's set, and feed `recorder.frames` into the finalize context. Each adapter captures frames while the recorder is still alive (service `onReload` → `#filmstripFrames`; Selenium `onDriverEnd` drain before nulling; Nightwatch `#finalizeCurrentScreencast` snapshot before delegating), and each finalize context spreads `[...accumulated, ...(live recorder frames)]` so a **mid-run** per-spec/per-test slice flush (which fires before the recorder is drained) isn't blank. When dense frames are present they **supersede** the sparse per-action filmstrip (the per-action DOM `elements`/`snapshot` are carried independently by the `frame-snapshot` events, so no DOM data is lost); a run without dense frames keeps the sparse filmstrip, byte-stable with before. Thinning is applied at export; the live session frame buffer is bounded by `maxBufferFrames` (default 2000; see the screenshot/video entry in `packages/service/CLAUDE.md`). Per-test filmstrip slicing follows the same per-test-hook availability as `traceGranularity:'test'` (works for WDIO mocha/cucumber, Selenium mocha, Nightwatch cucumber; Nightwatch `describe/it` and exports-object degrade to session scope per the entry in `packages/nightwatch-devtools/CLAUDE.md`), and non-Chrome polling carries the same reporter-noise caveat.

- Per-test artifact **Allure attachment** is cross-adapter via a pluggable sink in `core/allure-artifacts.ts` (`AllureAttachSink`; `captureAndAttachScreenshot`/`captureAndAttachVideo`/`attachTraceArtifact`/`lastRenderedScreenshot`). The service supplies a `@wdio/allure-reporter` sink; **Selenium** supplies an `allure-js-commons` `attachment()` sink (runtime-agnostic — attaches under any allure runner adapter — gated on `globalThis.allureTestRuntime`, dynamic-imported as an optional peer dep). An **undefined sink = produce-only** (write file + manifest, skip attach). Caveats: (a) **Selenium inline-attach needs awaited runner hooks** — its mocha `afterEach`/jest `afterEach`/cucumber `After` are async and awaited so the async produce+attach lands while the allure adapter still holds the current test open (fire-and-forget attaches to the next test or drops); Gherkin `AfterStep` is awaited too, so a step's trace slice, native app requests included, is written before the next step records its boundary. (b) **Nightwatch inline-attach is unsupported** — `nightwatch-allure` is post-hoc with no live attach API, and `allure-js-commons` no-ops in a Nightwatch run (nothing calls `setGlobalTestRuntime`); Nightwatch is produce-only. Revisit if an `allure-js-commons`-based Nightwatch runtime adapter appears (then it's a sink swap). (c) **video is standalone** in both adapters (recorder starts for `video != off` OR filmstrip in trace mode; the orphan session-webm encode is trace-gated to stop-only).

- **A wait is one row, and what it issued nests under it, in every adapter** (#464). A wait is one row named after what it waited for (`Element.waitForExist`/`Element.waitForDisplayed` on its selector for an element locator, `Browser.waitForFunction` for any other condition; a Selenium or Python locator wait is the command `waitForElementLocated`, a visibility wait `waitForElementVisible`), carrying a numeric `id`, sent when it starts with a `startTime` and no result or error, and replaced by that `id` when it ends, stamped at completion like every row. Every command its condition issued, an element wait's polls included, carries the wait's `id` as `CommandLog.parentId`, which shared documents generically as "the row whose execution issued this one". Shared `nestCommands` turns a flat row list into that tree, keeping a row whose parent is absent at the top level, so a live list rebuilt on each update nests it once the parent arrives; the dashboard's live list (`live-action-rows.ts`) and the player's tree (`action-tree.ts`, a `TraceActionCommandNode` with `children`) render the children under their row, collapsed unless the row failed or holds the active one. The trace exporter (`trace-action-events.ts`) writes a child's action with its parent's callId as `parentId` and closes the parent after its last child; the reader keeps an action in the trace vocabulary that other actions name as parent as a row rather than a structural step, so a foreign runner's steps are unaffected, and a stream without `parentId` exports byte for byte as before. Every adapter emits it: the service, Nightwatch and Selenium as their entries in `packages/service/CLAUDE.md`, `packages/nightwatch-devtools/CLAUDE.md` and `packages/selenium-devtools/CLAUDE.md` describe, and Python as follows. Its `wait_tracking.py` sends the wait's row from the patched `WebDriverWait.until`/`until_not` before the first poll and replaces it by `id` once the wait returns or raises; every row `execute` captures inside the condition takes the wait's id as `parentId` (`parent_of`) and still folds per call (`poll_of` / `note_poll_row`). A wait inside another's condition is a child of it and keeps one row across the outer polls, as a poll does, with the start of its first poll. `wait_row_name` names the row: `EC.presence_of_element_located` is `waitForElementLocated` and `EC.visibility_of_element_located` `waitForElementVisible`, on the locator converted the way `find_element` converts it (selenium's `LocatorConverter`, so `By.ID` reads `#x` like the element rows); anything else, `until_not` included, is `wait` on the condition's label, an `expected_conditions` closure named after its factory and captured arguments since its own name is `_predicate`. Naming runs before the user's condition, so it never raises (`_safe_label`, `_safe_row_name`), and a row that cannot be sent leaves the wait running. The conformance rule `wait-row-parents-its-commands` (`packages/conformance/src/wait-nesting.ts`) checks every scenario test shows exactly the waits it writes, each wait carries an id and a start, every row that ran inside a wait's span names it, and a parent is sent before its children; no adapter holds a gap against it. The comparison nests child steps under their parent (`NormalizedStep.children`) and compares the children of two aligned steps as their own aligned sequence, moves included.
  - **A poll that failed under a wait that did not fail is not a failure.** Shared `retriedRows` lists every failed row issued, at any depth, under a row that has not failed (a wait that passed, or one still running, whose outcome is not known yet), and `effectiveFailure` is `commandFailure` minus those. One rule serves every reader: the dashboard renders such a row neutral with its message in the row's title and leaves it out of the Errors tab, Copy prompt's Failures and a row's default expansion (`packages/app/src/components/workbench/actions.ts`, `packages/app/src/components/workbench/errors/collect.ts`, `packages/app/src/components/workbench/transcript.ts`), `transcript.md` marks it `RETRIED`, the trace writes its message as the after event's `retriedError` rather than `error` (`trace-action-events.ts`), the reader restores it onto `CommandLog.error` and restores `id`/`parentId` between action rows (`linkIssuedRows`) so the player judges it the same way, and the conformance comparison reads it as `ok` and never as the row that explains a failed test. Under a wait that failed, its children keep their errors, since the last poll's is what explains the timeout. A Nightwatch wait the aborted queue never ran is closed with a `NotRunError` at the test unit's end, so it counts as failed and its rows, having none, are unaffected.

- **`core/browser-focus.ts` `restoreBrowserFocus` (`open -a Safari`) has the Safari focus weakness the Selenium adapter avoids.** The WDIO service and Nightwatch still use `restoreBrowserFocus` once after session bring-up in live mode, with that weakness; a per-input switch there is the next step. Python has its own `restore_browser_focus` in `packages/selenium-devtools-py/src/selenium_devtools/device.py`, not checked for this weakness. The Selenium adapter's per-input window switch is described in `packages/selenium-devtools/CLAUDE.md`.
