# packages/selenium-devtools — design notes and known debt

Selenium adapter (`packages/selenium-devtools/src`): selenium-webdriver patching, the NetworkInspector wiring and the JS test-runner hooks.

## Known debt

- **A `wait()` poll is the user's one call, not a row per tick.** selenium-webdriver's `driver.wait(until.…)` runs its first poll inside the call, with the spec line on the stack, and every later one from a timer with no user frame, so a fold keyed on the call source left the first poll standing alone. The patched `wait()` runs its condition inside an `AsyncLocalStorage` (`wait-tracking.ts` `waitPoll`), which stamps `CapturedCommand.waitScope` (one object per `wait()` call) on exactly its own polls, per driver and per async chain, and `captureOrReplaceCommand` folds a poll **only** into the row an earlier poll of the same scope made for the same call (`WaitScope.rows`). The call is named at invocation (`waitPollOf`, `CapturedCommand.pollKey`) as the nth call with that command, args and target within one evaluation of the condition, since every evaluation repeats its calls in order and a timer poll has no call site to tell them apart: keyed on command and args alone, a condition reading `a.getText()` and `b.getText()` folded the second read over the first. A wait's rows never enter the ordinary retry tracker and reset it: replacing an older poll row moved only `lastId`, leaving `lastSig` naming another command, so a later retry of that command overwrote the wrong row, and a helper's wait polling the same `findElements` as a row the user wrote just before it overwrote that row. A retry therefore never folds across a wait. Captures run one at a time per capturer, because the driver patcher does not await `onCommand` and a poll could otherwise arrive before the previous one has the row id it folds into. A call outside a wait folds only as a same-call-site retry. Accepted cost: a library that polls from its own timer rather than through `driver.wait()` shows a row per poll.
  - **A wait is one row, and its polls are its children.** The patched `wait()` emits the wait's own row when it is CALLED (`openWaitRow`, `CapturedCommand.wait` naming its scope, `running`), stamped at its start with no result or error, and emits it again when the promise settles, stamped at completion and carrying the rejection as `error`; `captureOrReplaceCommand` captures the first and replaces it by id (`WaitScope.rowId`) with the second. Every row captured with that `waitScope` is stamped `parentId` = `rowId`, which is set by then because captures run in issue order and the running row is emitted before the condition first runs. A wait inside another wait's condition is a row of the outer one, and because its scope is kept across outer polls (`scopeFor`) it is one row re-sent running on each outer poll, from its first start, not a row per poll. The name comes from what the wait waits for: `tagElementConditions` wraps `until.elementLocated` and `until.elementIsVisible` and records each condition's target in a `WeakMap`, since the condition keeps its locator in a closure, so a locator wait is `waitForElementLocated` (`Element.waitForExist`) with the locator's `selector`, a visibility wait `waitForElementVisible` (`Element.waitForDisplayed`) with the selector the element was found by, and any other condition `wait` (`Browser.waitForFunction`) labelled with its `description()`; a locator with no selector form (link text) keeps the element name and puts the label in `args`. The running row takes no screenshot, drain or snapshot (`handleOnCommand` returns after the capture). The patched `wait()` returns a promise derived from selenium's that reports the outcome and passes it on, so an awaited failure rejects with the same error and an unawaited one still surfaces as `unhandledRejection`; an element wait is re-wrapped in selenium's own `WebElementPromise`, which `driver.wait(until.elementLocated(…)).getText()` chains on. A row that cannot be built is logged and never replaces the wait's own outcome.

Wait-row model: `packages/core/CLAUDE.md`.

- **Safari delivers a synthesized mouse click only to its frontmost window, and a live run opens the dashboard in another browser.** safaridriver's `performInteractionSequence` answers success either way, so a click issued while the Safari window is not frontmost reaches nothing: measured on desktop Safari 26.5 with no DevTools involved at all, the page reported `document.hasFocus() === false` (once `visibilityState: hidden`), no pointer event fired, and the submit never happened in 3 of 3 attempts, while after activating Safari every click landed; the user's own manual click in that window logged in. Live mode is where it shows, because the dashboard window and the wait for it to connect are what move focus; trace mode mostly escapes it and Chrome never has it. The Selenium adapter switches to the session's own window handle before every element click, sendKeys, clear and submit on a Safari session (`DriverPatcherHooks.beforeInput`, the plugin's `focusForInput`): a WebDriver window switch brings exactly that window forward, one round trip, and holds whatever took the front in between, measured 3 of 3 live logins against 0 of 2 before. `open -a Safari` was tried first and is not enough, since it activates Safari's most recent window, which can be the user's own (`visibilityState: hidden` in the automation window afterwards). The other adapters' `restoreBrowserFocus` weakness is in `packages/core/CLAUDE.md`. The Selenium dashboard also opens behind the current window on macOS for a Safari session (`dashboardLaunchCommand`, `open -n -g`).

- Selenium's `DETECTED_RUNNER` (the *detected JS runner* — mocha/jest/cucumber, from `detectRunner()`, `src/index.ts`) shadows the new `Metadata.runner` concept. The plugin internals expose it as `detectedRunner`, and `RerunManager` takes it as a constructor argument; the repo-wide rename in `plugin-internals.ts`/`session-lifecycle.ts` is still open.
