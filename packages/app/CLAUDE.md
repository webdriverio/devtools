# app — design notes and known debt

Owns the dashboard and trace-player UI, served by the backend and by the hosted player (`packages/app/src`).

### Backend and app are framework-agnostic

`backend` and `app` import from `shared` (for contracts) and from each other via the WS/HTTP boundary. Neither imports an adapter package. `backend` also imports `trace`, to write zips (it reads none: `show-trace` serves zip bytes and the app reads them); `app` imports only `trace`'s reader, which the hosted player (`trace.webdriver.io`, built with `pnpm player:hosted`, deployed by Vercel from `vercel.json`) runs in the browser to open a dropped zip with no backend at all. It runs the reader in a module Web Worker loaded from the player's own origin (`app/src/controller/trace-parse.worker.ts`, which `script-src 'self'` already admits), so the tab stays responsive and the landing screen names the phase the open is on; the live build never references the worker. The page posts the zip as a Blob and the worker keeps it open for as long as that trace is shown: the payload names frame images, stored bodies and page resources by zip entry, and the page asks the worker for each as it shows it (`controller/trace-entries.ts`, a byte-capped cache of Blobs and object URLs, revoked when evicted and when the next trace loads, which also terminates the worker). `show-trace` runs the same reader in the page, through the same `TraceArchiveClient`. When nothing is listed at `TRACE_API.run` the app also probes `TRACE_API.get`, which `start({ trace })` and backends from before the app read zips serve as a whole payload with its images inline (`shared` `LegacyTracePlayerData`); `controller/legacy-trace.ts` serves its inline images through an in-memory archive, so the published backend an adapter pins still pairs with a newer app. A trace is untrusted input, and its replay must run no script in any mode: the replay iframe is sandboxed (`allow-same-origin` only), `components/browser/replay-safety.ts` drops `<script>`, `on*`, `srcdoc` and `javascript:` URLs on the first render and on every replayed mutation alike, and the CSP (`packages/shared/src/player-csp.ts`) blocks what the first two miss, and admits `blob:` in `style-src`, `font-src`, `img-src` and `media-src`, which is where the replay serves a trace's stored stylesheets, fonts, images and media (`components/browser/archived-resources.ts`, typed by kind so a crafted trace cannot make a blob a document); the hosted e2e check opens a hostile trace to prove it. The backend sends `playerCsp()` on its HTML and `vercel.json` carries the hosted policy as a literal, which `packages/conformance/tests/hosted-player-expectations.test.ts` holds to `hostedPlayerCsp()` and to differ from the backend's in `connect-src` alone: the hosted page admits `https:` there so `?trace=<url>` can download a zip (`controller/trace-download.ts`: https or the page's own origin only, no credentials or referrer, a redirect off https refused, nothing received for `TRACE_DOWNLOAD_IDLE_TIMEOUT_MS` aborts it, the body is refused at its first chunk unless it starts as a zip and cut off at `TRACE_DOWNLOAD_MAX_BYTES`, which bounds the download and the archive the tab holds; its entries are read one at a time as they are shown). `trace` is read as everything after `trace=` when it starts with a scheme or `/` (`utils/trace-link.ts` `traceParamFrom`), so an unencoded signed URL keeps its own `&` parameters, and as an encoded value up to the first raw `&` otherwise. That widening is a trade: the player's own script could now reach any https host, which is why everything else stays `'self'` and the replay stays script-free; `show-trace` and the live dashboard keep the backend's `connect-src` (`'self'` plus the dashboard socket) and have no `?trace=`. A position in an opened trace lives in the hash, `#action=<callId>&tab=<tab>` (`shared/trace-player.ts` `parseTraceLink`/`formatTraceLink`), and `controller/trace-link.ts` and `utils/trace-link.ts` are the code that read or write the address (`trace-open.ts` also reads the `trace=` parameter): the reader keeps each action's zip `callId` on `CommandLog.callId`; the controller applies the page's link once, to the first trace shown, by asking the timeline (`PLAYER_SEEK_ACTION_EVENT`) and the player dock (`OPEN_DOCK_TAB_EVENT` with `linked`) once each has announced itself (its first `show-command`, `DOCK_TABS_READY_EVENT`), applies it again only on a `hashchange`, and writes each later pick back with `history.replaceState`. A trace the viewer opens by hand (`TraceOpenController`'s `onUserOpen`) clears the hash and `?trace=`, or the link would steer a trace it was never about; while several traces are open as a run it neither writes nor applies `action`, since the hash names no run entry. The clock the timeline places itself (opening, or following a link) is announced with `keepTab`, so the Log tab's follow-the-selection does not override the linked tab. That build is `HOSTED_PLAYER` in `app/src/controller/constants.ts`; it never writes the trace to browser storage, and `vercel.json` is also what `vite preview` serves, so its CSP is checked locally before it ships. Several zips or a folder open as a run (`controller/trace-run.ts`), in the hosted player and in `show-trace`, which lists the zips it serves at `TRACE_API.run` for the app to read (a single zip is a listing of one, which the app opens straight into the player): each zip is read once, one at a time, for its summary alone, and opened again when its row is picked. A zip records no test state, so a row's outcome is read from its rows (`utils/trace-summary.ts`: a failed action or step means failed, actions with none failed mean passed, no actions mean unknown); a jest `expect` that records no row can therefore fail a test whose trace reads as passed.

## Design notes

- **Two unrelated events share the `clearExecutionData` scope, and the receiver cannot tell them apart from the uid.** A run STARTING (`backend/src/index.ts` `handleTestRun`, one per `POST /api/tests/run`) and ONE ENTRY resetting inside a run already in flight (`nightwatch-devtools/src/cucumber-lifecycle.ts`, which re-emits a scenario suite and must not wipe its siblings) arrive under the same scope with the same shape. The app inferred the difference by comparing the uid against `rerunState.activeRerunSuiteUid` — a latch that outlived its rerun, so the *next* run start at a different scope read as a child clear of the last one and **skipped its wipe entirely**: rerun a suite, then the file or Tests, and the Actions/Console/Network tabs kept the previous run's rows and grew with each rerun. `ClearExecutionDataWsPayload.runStart` now states it on the wire (it has to be on the wire, not local to the clicking window — popouts see only WS events), and the app clears both latches when it is set. A backend test asserts the flag actually ships: the app-side fix reads it, so dropping it would restore the bug with every app test still green.

## Known debt

- **A live client receives commands in ARRIVAL order, so a consumer that bounds a row by its neighbour orders by time first.** Nightwatch withholds native asserts until their outcome is known and flushes them in one batch at test-end (BDD fires `afterEach` once per *module*, so a whole module's asserts arrive after every driver row). The display list already sorts and `utils/elapsed.ts` already treats capture order as untrusted, and `app/src/components/browser/mutation-at-command.ts` orders a row's successor by `(startTime ?? timestamp, sequence ?? 0, array index)` — the key `buildActionEvents` uses, with the index last so a chronologically ordered array (every trace) resolves to its own successor. Bounding by `commands[idx + 1]`, the *array* neighbour, bounds a row by a time before it ran: the run's last `waitForElementVisible('#username')` takes its bound from an assert that ran 7.6 s earlier and replays `/secure`. Live-mode anchoring itself is not the gap: `processTracePayload` sends mutations upstream unconditionally, and a live run streams one anchor per document visited.
  - Residual: a submit click whose end, destination birth and next command's start land in the **same millisecond** still shows its pre-navigation page; and the app deliberately leaves the **last** row unbounded, rendering the newest DOM.

- Still open, same class: `packages/app/src/components/browser/snapshot.ts` `#videos` is only ever pushed to, so the screencast "Recording N" dropdown accumulates every session of every run for the life of the page (observed at 17). That component listens only to the `screencast-ready` window event and never learns a run started.
