# packages/service — design notes and known debt

WebdriverIO service plugin (`packages/service/src`): WDIO hook binding, the command stack, and expect-webdriverio folding.

## Design notes

### One DOM snapshot per action, taken before it

In the WDIO service the per-action trace snapshot is captured in `beforeCommand`, stamped at the previous action's end, so an action's result IS the next action's "before" and every row resolves to a state the driver was idle for. Its `afterCommand` captures nothing in trace mode. An eager post-action capture — added and removed twice — lands while the screen is still moving, which is the only reason `waitForActionResult` and the `__wdioSnapMark` document tag existed; both are deleted. The last action has no successor, so `#finalizePerScenario` supplies it and names its capture after that action — `lastRenderedScreenshot` skips a capture named `__final__`, which is reserved for a session that ran no action at all. What that one capture waits on is `settleAfterLastAction`, and the wait is **gated, not timed**: the drain that runs immediately before it (`captureTrace(browser, true)`) anchors each document once, so `SessionCapturer.replacedDocumentInLastDrain` says whether the last action navigated to a document the session had not seen. No → return at once (the app has been at rest since the last action, so the test's own teardown is the gap that let the paint land). Yes → `waitUntil(document.readyState === 'complete')`, which is only meaningful once you know the document being described is the incoming one: ungated, the OUTGOING document already reports 'complete' right after a click, so a blind poll returns instantly and captures the page the test just left, and the old `body.childElementCount > 0` clause that papered over that made a legitimately blank destination a guaranteed 8 s timeout per test. Native pauses 250 ms instead (no document to poll; a capture at a 0 s gap measures 359–476 KB against 1.87 MB settled on Appium). Nightwatch re-captures a command whose capture predates the destination document's `performance.timeOrigin` (a navigation that committed after it returned), and discards that re-capture if a newer page capture was queued meanwhile. Residual: a navigation that has not *committed* when the anchor is read still reads as "no navigation" — the same blind spot the deleted document tag had. Don't reintroduce a poll without a gate, or a tag.

Cross-adapter capture-gate rules (`skipsCapture`, the end-of-test frame, Python's filmstrip-only frames) are in `packages/core/CLAUDE.md`.

Capture cost: `.claude/rules/capture-cost.md`.

## Known debt

- The per-test `screenshot` and `video` options live on the **WDIO `ServiceOptions` only** — not `BaseDevToolsOptions` — because only the service implements them (an option belongs on an adapter until a second adapter consumes it, mirroring the core-helper rule; putting them on the shared base made them appear available in Selenium/Nightwatch and broke those adapters' `Required<>` option types). The policy *types* (`TraceScreenshotPolicy`/`TraceVideoPolicy`) and the capture/slice/encode logic (`core/screenshot-artifact.ts`, `core/video-slice.ts`) are framework-agnostic, so Selenium and Nightwatch wire them on their own options (Selenium on its `DevToolsOptions` with full inline attach; Nightwatch produce-only — see the Allure-attach entry in `packages/core/CLAUDE.md`). All are gated to `traceGranularity:'test'` (per-test inline Allure); coarser granularities keep artifacts in the manifest. Video records the screencast continuously and slices per-test by wall-time — the session frame buffer is bounded by `maxBufferFrames` (default 2000; decimates keeping first/last), and on non-Chrome the polling recorder issues many `takeScreenshot`s that flood `@wdio/allure-reporter` (pair with `disableWebdriverStepsReporting`).

- Service renders expect-webdriverio matchers as single `expect.<matcher>` rows by **folding**, not stack/depth suppression. The matcher's value-read (`toHaveText`→`getText`, `toExist`→`isExisting`, …) is captured as a normal command; `afterAssertion` then coalesces the synthesized `expect.*` row into that read in place — inheriting its callSource, screenshot, and timeline position — and the fold replaces **by timestamp**, because a top-level read carries no public `id`: only a wait and the rows it issued do, drawn from core's `commandCounter`, which starts at a random base per capturer so ids stay unique across specs and workers (entry below). `beforeAssertion` arms the pending matcher (depth-counted so aliases like `toBeChecked`→`toBeSelected` fold once); a matcher that **hard-throws** — element never resolves, so expect-webdriverio's `waitUntil` rethrows and `afterAssertion` never fires — is synthesized at `afterTest`/`afterStep` from the throwing read, so a failing assertion renders as `expect.<matcher>` whether or not the element existed. Two limits: its error is then the read's (`Can't call getText on … element wasn't found`), not an assertion-phrased message; and `MATCHER_READ_COMMANDS` is a hand-maintained allowlist, so a matcher whose read isn't listed leaves its raw read visible alongside the `expect.*` row. Plain-value jest matchers (`expect(x).toBe(y)`) don't fire the ewdio hooks, so they aren't captured as rows. Only these matcher rows inherit the selector resolved during the matcher (`captureMatcherCommand`); a node:assert row takes its target from the value registry (`captureAssertCommand`, see the value-provenance entry in `.claude/rules/assert-capture.md`). `toHaveTitle` folds into the user-visible `getTitle` read like any other listed read, while `getUrl` is in `MATCHER_READ_COMMANDS` (`src/assert-capture.ts`) and still in `INTERNAL_COMMANDS` (`src/constants.ts`), so the read is hidden and `toHaveUrl` emits a fresh row.

- **The WebdriverIO service logs the command on top of its stack, and inside a wait, the commands the wait issued.** WDIO fires `beforeCommand`/`afterCommand` for every command at every depth, so the service has always kept a row only for the command a spec issued with nothing else running, and hidden what that command issued. A wait (`waitUntil` and the element `waitFor*` family, read off ACTION_MAP) is the one exception: `command-stack.ts` `CommandStack` opens a level under it, and every command the wait issued directly becomes a row with the wait's `id` as `parentId`, while what those issue stays hidden, the same rule one level down, so a wait inside a `waitUntil` condition nests again. The wait is sent running from `beforeCommand` with an id from core's random-base counter (`wait-rows.ts` `WaitRows`), replaced by that id at completion and moved to the end of `commandsLog`, which keeps the log in completion order for every scan that reads its tail (`failLastAction`, the matcher fold, `#lastAction`). Its children carry ids too, so each distinct call folds by id rather than by timestamp; rows outside a wait still fold by timestamp. Three details are load-bearing. An element wait polls through its own `waitUntil`, which is its implementation and never a row, and WDIO fires an element command's hooks twice, the first from its element wrapper with no arguments, so a wait opened with none skips the same command's next hook before it issued anything; that is decided by the arguments, not the stack, which carries the spec frame on both hooks once it is searched 40 frames deep. Commands the service issues from its hooks are told apart by an `AsyncLocalStorage` (`runAsServiceWork`), not by their stack, because a wait's polls carry no spec frame either. And the hook methods are deliberately not `async`: WDIO keeps one module-global `inCommandHook` flag and skips every command's hooks while any hook is running, so a hook that settles a few microtasks later drops a concurrent command's hooks (measured: an `emit` hook running during `elementClick` made the submit click's `afterCommand` never fire, and the click lost its row). The selector a condition located is restored when its wait ends, so `el.click()` after a wait still reads the element's own. A matcher never folds into a read a wait issued.

Wait-row model: `packages/core/CLAUDE.md`.

## File size

- `packages/service/src/index.ts` (over the 500-logic cap). Which commands become rows, and the wait nesting that decides it, live in `command-stack.ts`, and the wait rows themselves in `wait-rows.ts`. The screencast and trace-slice seams are extracted: `screencast-lifecycle.ts` owns every read and write of recorder frames — start, reload, finalize, the cross-`reloadSession` filmstrip buffer and the per-test video slice, two invariants that were previously produced and consumed 400 lines apart — and `trace-slices.ts` owns boundary recording plus the eager per-test flush beside the flush I/O it already held. The only remaining cluster large enough to close the gap is the command-hook family (`beforeCommand`/`afterCommand`/`#commandStack`/`#drainAfterLiveCommand`, ~120 logic lines); `before()` is still over the function cap at 51 logic lines.
